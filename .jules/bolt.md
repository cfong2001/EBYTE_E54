## 2026-04-25 - [Memory Leak Prevention in High-FPS Menus]
**Learning:** Initializing an array of Arduino `String` objects (e.g. `String items[24];`) inside a high-frequency display loop (like `drawMenuOverlay` called at 30Hz) causes rapid heap fragmentation and subsequent CPU stalls as the ESP32 struggles to garbage-collect and reallocate memory continuously.
**Action:** Always declare string arrays used for high-frequency UI rendering as `static` (e.g. `static String items[24];`) or elevate them to class members. This prevents continuous memory allocation/deallocation overhead, vastly improving UI responsiveness.
## 2025-04-25 - HardwareSerial Buffer Size Optimization
**Learning:** For ESP32 hardware using high-speed UART (like 256000 bps for E54 radars), the default 256-byte HardwareSerial RX buffer can easily overflow within ~10ms if `loop()` execution delays.
**Action:** Use `HardwareSerial::setRxBufferSize(1024)` before calling `begin()` when working with baud rates 115200 or higher to prevent packet loss and improve reliability.
## 2024-05-19 - Defer math.sqrt calls in display loops
**Learning:** Found a performance bottleneck where `math.sqrt()` was being called on every target inside rendering loops solely to find the minimum distance for text display. On constrained embedded hardware, evaluating `math.sqrt` inside tight loops causes measurable overhead.
**Action:** When finding the closest target distance, track `closest_dist_sq` by calculating squared distances (`x*x + y*y`) inside the loop, and apply `math.sqrt()` to the final `closest_dist_sq` outside the loop before rendering.

## 2026-04-25 - [Single Precision Float Math Optimization]
**Learning:** Using standard double precision math functions (`sqrt`, `sin`, `cos`, `atan2`, `abs`) implicitly casts variables back and forth to double when dealing with `float` types. For the ESP32 platform, utilizing single precision variants (`sqrtf`, `sinf`, `cosf`, `atan2f`, `fabsf`) uses the hardware FPU natively and prevents the type casting overhead.
**Action:** Default to using single precision functions (e.g. `sinf`, `sqrtf`, `fabsf`) whenever the data variables are strictly typed as `float`. Avoid implicit type promotion in constrained performance-critical paths.

## 2024-05-18 - [Optimization] ESP32 Performance Enhancements
**Learning:** For optimal ESP32 rendering with TFT_eSPI, especially on screens sized 240x240 and above, initializing DMA (`tft.initDMA()`) combined with full-frame sprites enables PSRAM usage (if available) and allows the display transfer to occur concurrently with CPU logic (`tft.pushImageDMA()`). Pinning radar read processing to Core 0 with `xTaskCreatePinnedToCore` provides uninterrupted UI and inputs on Core 1 while securing serial data perfectly.
**Action:** Always enable DMA for heavy UI processing on ESP32 and distribute time-critical serial polling and UI rendering across separate cores using FreeRTOS tasks and mutexes for safety.
## 2024-04-26 - ESP32 Dual-Core FreeRTOS Performance Profiling
**Learning:** Measuring ESP32 FreeRTOS core execution and idle times using `uxTaskGetSystemState` is extremely powerful for diagnosing execution bottlenecks but causes C++ compilation errors (`undefined reference`) on default ESP32 toolchains unless custom ESP-IDF SDK configuration (`CONFIG_FREERTOS_USE_TRACE_FACILITY`) is explicitly compiled into the underlying framework core.
**Action:** When profiling standard Arduino-ESP32 setups, fallback to utilizing standard FreeRTOS APIs like `uxTaskGetNumberOfTasks()` and `ESP.getFreeHeap()` / `ESP.getMaxAllocHeap()` embedded in a low-priority modular background task (`xTaskCreatePinnedToCore`) rather than relying on advanced trace metrics unless the framework is explicitly built with trace support.

## 2024-05-19 - Pre-computing Trigonometric Tables for UI Rendering in Python
**Learning:** Found a performance bottleneck where `math.cos()` and `math.sin()` were being called repeatedly inside UI rendering loops (e.g., drawing dotted circles). In constrained embedded environments like CircuitPython, evaluating trigonometric functions dynamically is computationally expensive.
**Action:** Created static, module-level lookup tables (`COS_TABLE` and `SIN_TABLE`) mapping 0-359 degrees to their pre-computed sine and cosine values. Replaced dynamic calls with integer modulo arithmetic (e.g., `int(round(angle)) % 360`) to index the tables, resulting in significant performance gains for UI drawing.

## 2026-05-04 - [Handheld Radar Optimization with Temporal and Procrustes Processing]
**Learning:** Hardcoded delta time (`dt = 0.1s`) leads to severe tracking jitter on embedded devices where loop execution time is highly variable (e.g., due to background WiFi/SD tasks). Using high-resolution hardware timestamps (via `micros()`) tied exactly to serial packet boundaries (e.g., parsing the 0xCC tail byte) ensures the Alpha-Beta-Gamma filters operate accurately. Additionally, for handheld sensors, raw background reflections appear to translate wildly. By performing rigid-body procrustes analysis across static anchors, the UI can achieve true gimbal-like motion compensation natively, without relying on physical IMU components. Dynamic resolution weighting provides instant gain selection to balance track continuity vs lag. Mahalanobis Gating efficiently rejects invalid ghostly sensor reflections that teleport in unphysical timespans.
**Action:** Always track variable time delta (`dt`) at the exact boundary of a completed sensor transaction when developing tracking filters on real-world platforms, and utilize spatial distance gating to reject erroneous background detections from active environments.
## 2026-05-04 - [Parametric Filtering for Handheld Video Stabilization]
**Learning:** From the Video Stabilization survey article, applying a mathematical gate with a fixed minimum noise floor ensures targets aren't artificially filtered when temporal deltas (`dt`) become very small due to fast consecutive frames. Furthermore, applying an Exponential Moving Average (EMA) (Section 2.1.2: Parametric Filtering) to the rotational transform components (cosT, sinT) effectively filters out high-frequency sensor shakes from active handheld panning maneuvers.
**Action:** Always enforce a `baseNoiseFloor` threshold when bounding speed/distance formulas that depend linearly on time deltas to prevent over-gating. Employ basic parametric filters like EMA on global transformation matrices before applying them to dynamic targets to stabilize rotational data streams.
## 2026-05-04 - [MeshFlow-Inspired Real-Time Trajectory Optimization for Embedded Systems]
**Learning:** Dense grid-based mesh warping algorithms (like `MeshFlow`) are too heavy for single-core, low-memory embedded targets like the ESP32. However, the core principle of using a Gaussian-weighted spatial smoothing window applied to historical vertex profiles is extremely effective for stabilizing jittery point coordinates. By storing a tiny circular buffer (e.g. `15 frames`) of historical (x, y) target coordinates, we can apply an exponential Gaussian spatial weight based on the time delta `(r-t)` inside the target update loop.
**Action:** Always maintain a historical coordinate buffer (`historyX`, `historyY`) for tracked objects and apply Gaussian time-decaying weights to construct a "smoothed objective coordinate" rather than relying strictly on the instantaneous frame output from sensors.
## 2026-05-04 - [Drop-out Resilience via Forward Prediction coasting]
**Learning:** Tracking filters fail and completely reset their stabilization matrices when physical sensors momentarily "lose" a target for 1-3 frames. This destroys the historical optimization buffer and creates visual flickering. By maintaining a `framesLost` counter and coasting the target forward using its last known velocity vector (`P_x = P_x + V_x * dt`), we can artificially maintain the tracking state.
**Action:** When working with sporadic RF/Vision data, always implement a "Grace Period" (`maxFramesLost`) using kinematic forward-prediction so momentary sensor blindness does not destroy long-term statistical tracking data.
## 2026-05-04 - [Velocity-Adaptive Temporal Windowing]
**Learning:** Extending the historical Gaussian tracking window (e.g. from 15 to 30 frames) provides exceptionally deep stabilization for static objects but induces physical lag when a target begins moving rapidly. By computing the target's current speed (`sqrt(velX^2 + velY^2)`) and dynamically multiplying the effective Gaussian `window_size` by an inverse speed factor, the tracking filter immediately drops stale history when the target accelerates.
**Action:** When using sliding historical windows or EMA buffers for coordinate stabilization, always bind the effective window size/decay rate to the entity's velocity. This ensures "lock-in" stability when still, and zero-lag tracking when moving.
## 2026-05-04 - [UI Visualization for Tracker Debugging]
**Learning:** Understanding whether the internal filter state has "locked in" (tight tracking window) or is spreading out due to noise or rapid movement is difficult when observing just a single computed coordinate dot.
**Action:** When developing complex trajectory optimization logic, calculate and expose the mathematical Standard Deviation (or variance) of the tracking buffer. Pass this variable to the UI to render an alpha-blended confidence circle (or bounding box) around the entity, allowing developers to visually confirm exactly how the temporal smoothing buffers are reacting to input stimuli.
## 2024-05-18 - Queue over Mutex & Compile-Time Trigonometry
**Learning:** Mutexes between high-frequency UART parse tasks and UI render loops can cause severe scheduler contention, destroying real-time hardware responsiveness. Additionally, standard `sinf`/`cosf` calls in rapid UI loops consume excessive CPU cycles and trigger floating-point stalls.
**Action:** Always use FreeRTOS queues (like `QueueHandle_t`) for passing deterministic frame payloads asynchronously. Implement compile-time static `constexpr` trig tables (accessed via modulo 360 arithmetic) to bypass the FPU for performance-critical rendering loops.
